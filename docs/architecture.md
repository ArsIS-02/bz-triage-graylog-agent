# Архитектура

## Задача

Собирать телеметрию macOS (активность, persistence, baseline) с парка
машин и централизованно анализировать в Graylog — без разработки
собственного EDR-агента.

## Решение

`bz_triage` как коллектор + три `launchd`-агента с разными профилями
и разной частотой + Graylog как центральный анализатор.

## Схема

```text
┌──────────────────┐   JSON Lines   ┌───────────────┐
│ bz_triage        │ ────────────>  │   Graylog     │
│ + bzt-filter.pl  │  Raw TCP :9095 │  Raw/Plaintext│
│ + nc             │                │  + JSON       │
└──────────────────┘                │  Extractor    │
                                    └───────────────┘
```

## Почему три агента, а не один

Один агент с одним интервалом имеет жёсткое ограничение: интервал
должен быть в 2–3 раза больше времени сбора **самого тяжёлого**
профиля в наборе. Если в наборе `autoruns` (30–60 сек), часто
запускать нельзя — запуски начнут накладываться.

Разделив профили по частоте изменений, получаем:

| Что | Как часто нужно | Агент |
|-----|-----------------|-------|
| Активность (процессы, сеть, сессии) | 5–15 мин | `activity` |
| Persistence (autoruns, cron, launchd) | 15–30 мин | `persistence` |
| Полный baseline (investigation) | 1 раз в сутки | `baseline` |

**Плюсы:**

- `activity` и `persistence` не блокируют друг друга (разные
  лок-файлы, per-profile lock).
- Тяжёлый `autoruns` не тормозит лёгкий `netconn`.
- Можно регулировать каждый независимо — увеличить интервал
  одного, не трогая остальные.
- Логи раздельные — легче диагностировать.
- Можно отключать выборочно (например, выключить `persistence`
  на время работ).

**Минусы:**

- Три plist-а вместо одного.
- Больше логов и лок-файлов.
- Чуть выше сложность поддержки.

## Почему не Filebeat / Logstash / Vector

- `bz_triage` уже умеет `--stdout`, дополнительный шиппер не нужен.
- Никаких JVM/Python на хостах — меньше поверхность атаки.
- `nc` — родной для macOS, не требует установки.
- Меньше движущихся частей — проще диагностировать.
- Меньше зависимостей — меньше ломается при обновлениях.

## Почему `--stdout | nc`, а не `--dstaddr`

У `bz_triage` есть встроенный `--dstaddr=ADDR --dstport=PORT`.
Но при его использовании сенсор **всё равно пишет артефакты на диск**
(в `--outdir` или cwd), и это лишний расход места.

Схема `--stdout | filter | nc`:

- ничего не пишет на диск,
- даёт возможность фильтровать данные на хосте (`bzt-filter.pl`),
- не создаёт проблем с переполнением диска.

## Почему не один общий lock на всё

Общий `lock /var/run/bzt.lock` означает, что `persistence` не сможет
стартовать, пока работает `activity`. С per-profile локом
(`/var/run/bzt.<profiles>.lock`) оба работают параллельно.

## Почему lock с PID, а не просто mkdir

Если процесс убит SIGKILL (например, systemd при жёстком ребуте),
`trap` не срабатывает и лок-директория остаётся. Следующий запуск
видит `another run is active` и никогда не стартует.

Решение: писать PID владельца в `lock/pid` и при старте проверять —
жив ли он. Если нет — снести лок.

## Поток данных

1. `launchd` запускает `bzt-stream.sh` по расписанию.
2. Скрипт создаёт `mktemp -d` для временных файлов.
3. `bz_triage` собирает данные в `stdout`.
4. `bzt-filter.pl` удаляет тяжёлые поля (`file_content`, YARA).
5. `nc -w 180` отправляет JSON Lines на Graylog:9095.
6. `trap` снимает лок и удаляет временную директорию.

## Ограничения

- `bz_triage` не демон — запускается по расписанию `launchd`.
- Интервал запуска должен быть больше времени сбора самого тяжёлого
  профиля в наборе.
- При большом `autoruns` `nc` может вернуть ошибку на закрытии —
  используем `|| true`, чтобы скрипт не падал.
- На macOS нет GNU `timeout` — не используем его в скриптах.
