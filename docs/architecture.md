# Архитектура

## Задача

Собирать телеметрию macOS (активность, persistence, baseline) с парка
машин и централизованно анализировать в Graylog — без разработки
собственного EDR-агента.

## Решение

`bz_triage` как коллектор + три `launchd`-агента с разными профилями
и разной частотой + Graylog как центральный анализатор.

## Схема

```text
┌──────────────────┐   JSON Lines      ┌───────────────┐
│ bz_triage        │ ──────────────>   │   Graylog     │
│ + bzt-filter.pl  │  Raw TCP :<порт>  │  Raw/Plaintext│
│ + nc             │                   │  + JSON       │
└──────────────────┘                   │  Extractor    │
                                       └───────────────┘
```

## Почему три агента, а не один

Один агент с одним интервалом имеет жёсткое ограничение: интервал
должен быть в 2–3 раза больше времени сбора **самого тяжёлого**
профиля в наборе. Если в наборе `autoruns` (30–60 сек), часто
запускать нельзя — запуски начнут накладываться.

Разделив профили по частоте изменений, получаем:

| Что | Как часто нужно | Агент |
|-----|-----------------|-------|
| Активность (процессы, сеть, сессии) | 5–15 мин | `activity` |
| Persistence (autoruns, cron, launchd) | 15–30 мин | `persistence` |
| Полный baseline (investigation) | 1 раз в сутки | `baseline` |

**Плюсы:**

- `activity` и `persistence` не блокируют друг друга (разные
  лок-файлы, per-profile lock).
- Тяжёлый `autoruns` не тормозит лёгкий `netconn`.
- Можно регулировать каждый независимо.
- Логи раздельные — легче диагностировать.
- Можно отключать выборочно.

**Минусы:**

- Три plist-а вместо одного.
- Больше логов и лок-файлов.

## Почему `--stdout | nc`, а не `--dstaddr`

У `bz_triage` есть встроенный `--dstaddr=ADDR --dstport=PORT`.
Но при его использовании сенсор **всё равно пишет артефакты на диск**
(в `--outdir` или cwd), что лишний расход места.

Схема `--stdout | filter | nc`:

- ничего не пишет на диск,
- даёт возможность фильтровать данные на хосте (`bzt-filter.pl`),
- не создаёт проблем с переполнением диска.

## Почему не Filebeat / Logstash / Vector

- `bz_triage` уже умеет `--stdout`, дополнительный шиппер не нужен.
- Никаких JVM/Python на хостах — меньше поверхность атаки.
- `nc` — родной для macOS, не требует установки.
- Меньше движущихся частей — проще диагностировать.

## Почему `StartCalendarInterval`, а не `StartInterval`

`launchd` поддерживает два вида таймеров:

| | `StartInterval` | `StartCalendarInterval` |
|-|-----------------|--------------------------|
| Как работает | Запуск через N секунд после **предыдущего старта** | Запуск в указанные минуты календаря |
| Активация | Требует `kickstart` после `bootstrap` | Не требует |
| После сна | Пропущенные окна теряются | Догоняет — запускается сразу после пробуждения |
| Точность | ±N сек | ±сек от календарной минуты |
| Поведение при `bootout/bootstrap` | Сбрасывается | Сохраняется |

**Мы используем `StartCalendarInterval` по всем трём агентам.**

Причины:

1. **Не залипает.** `bootstrap` без `kickstart` не сработал бы с
   `StartInterval` — агент остался бы с `runs = 0` и не запустился
   никогда. С Calendar — сработает в ближайшую подходящую минуту.
2. **Не теряет данные после сна.** Ноутбук, открытый утром, сразу
   отправит пропущенный прогон.
3. **Расписание видно в plist-е.** Понятно, что и когда запускается,
   без пересчёта интервалов.

## Почему `RunAtLoad = true`

Дополнительная страховка: при каждой загрузке Mac или `bootstrap`
агент запустится **один раз сразу**. Это разрывает потенциальный
замкнутый круг «таймер ждёт первого запуска, а первый запуск ждёт
таймера».

## Сдвиг минут между хостами

Если несколько Mac'ов работают с одинаковым расписанием, они
одновременно бьют в Graylog. На пике это даёт всплеск нагрузки.

Решение — сдвигать минуты по хостам:

| Хост | activity | persistence |
|------|----------|-------------|
| Хост #1 | `:00, :10, ...` | `:05, :35` |
| Хост #2 | `:02, :12, ...` | `:07, :37` |
| Хост #3 | `:04, :14, ...` | `:09, :39` |

Сдвиг по 2 минуты на каждый следующий хост. При 10 хостах:
`:00, :02, :04, :06, :08, :10, :12, :14, :16, :18` — все разные.

## Почему lock с PID, а не просто mkdir

Если процесс убит SIGKILL, `trap` не срабатывает, и лок-директория
остаётся. Следующий запуск видит `another run is active` и никогда
не стартует.

Решение: писать PID владельца в `lock/pid` и при старте проверять —
жив ли он. Если нет — снести лок.

Плюс: **lock per-profile** — разные агенты (`activity` и
`persistence`) не блокируют друг друга.

## Поток данных

1. `launchd` запускает `bzt-stream.sh` по расписанию.
2. Скрипт создаёт `mktemp -d` для временных файлов.
3. `bz_triage` собирает данные в `stdout`.
4. `bzt-filter.pl` удаляет тяжёлые поля (`file_content`, YARA).
5. `nc -G 5 -w 1` отправляет JSON Lines на Graylog.
6. `trap` снимает лок, удаляет временную директорию и чистит
   `edr-data*` и `bzt.*` старше 10 минут.

## Ограничения

- `bz_triage` не демон — запускается по расписанию `launchd`.
- Интервал запуска должен быть больше времени сбора самого тяжёлого
  профиля в наборе.
- При большом `autoruns` `nc` может вернуть ошибку на закрытии —
  используем `|| true`.
- На macOS нет GNU `timeout` — не используем его в скриптах.
- `--limit-time` у `bz_triage` не убивает дочерние `bzsenedrcore` —
  если процесс завис, приходится убивать `pkill -9`.
